## Context
Three facts git does not keep, or that cost too much to read in a short session:
- **When a commit reached the trunk.** Git keeps when a commit was made; a rebase made hours earlier or a
  wrong clock gives the wrong date.
- **The state without the history.** In a very large repo the SessionStart fetch may not fit its cap.
- **What runs in each environment**, without GitHub's API.

So:
- A CI job `ledger-snapshot` runs on every push to the trunk and every tag, with `permissions: contents:
  write`, `concurrency: ledger-snapshot` and the full history. `ledger.py snapshot` writes `LEDGER.md` and
  `ledger.json`, and appends to `moves.toml` the trunk SHA, the time the CI saw it and the run id. It
  commits with git plumbing in a temporary index (never touching a checkout) to the orphan branch
  `keelokit/ledger`, and on a rejected push starts again from the new tip, up to 5 times, as Harbor does
  with its logbook.
- Readers use the snapshot when the history is incomplete (`history = "snapshot:<sha>"`; if its SHA is not
  the current trunk it says how old it is and computes what it can), and take the exact arrival time from
  `moves.toml` (`since_exact = true`). `history --ensure` reads the snapshot when the fetch is cut.
- The template's deploy jobs (`release.yml.jinja`), when a deploy succeeds, move `deploy/staging` or
  `deploy/production` to the deployed commit, backwards too on a rollback. `ship-setup` explains them.
- `[ledger] snapshot = ""` turns the job and the reading off.

Does NOT do: use GitHub's API; publish anything outside the repo.

## User story
As a session with little time or a huge repo, and as the person who asks what runs in production since
when, I want those facts recorded by the CI as they happen, so that the ledger can answer exactly.

## Acceptance criteria
```gherkin
Scenario: [S1] A push to the trunk is recorded
  When `ledger.py snapshot` runs after a push
  Then keelokit/ledger has that SHA in moves.toml with the time and the run, and LEDGER.md and ledger.json for it

Scenario: [S2] Two pushes in a row
  Given two snapshots racing for the branch
  Then both moves are recorded, in order, and none is lost

Scenario: [S3] A shallow session reads the snapshot
  Given a shallow clone whose fetch is cut
  Then the ledger reads the snapshot, says so, and gives states as of its SHA

Scenario: [S4] A production deploy
  Given the deploy job moved deploy/production to a commit that contains AUTH-001's
  Then AUTH-001 is in-production

Scenario: [S5] A rollback
  Given deploy/production moved back to before AUTH-001's commit
  Then AUTH-001 is no longer in-production

Scenario: [S6] Turned off
  Given `snapshot = ""`
  Then the template's CI has no snapshot job and the ledger reads none

Scenario: [S7] The whole walk in a generated project
  Given a project generated by scripts/test-template.sh and a local remote
  When a session takes a story, commits, lands with Story:, tags, and the deploy branch moves
  Then `ledger.py show` reaches in-production and nobody wrote a state
```
