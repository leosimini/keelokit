- **Persona / context:** Every persona, every render: this is the above-the-fold "Where we are" hero, the first thing anyone sees on `/keelokit:project-dashboard`, in both light-mode-only elements (the sea band ignores `prefers-color-scheme`/`data-theme`, it's always the dark gradient) and both languages. Sha 19b332e.
- **Steps:**
  1. `git clone /home/user/keelokit $SCRATCH/keelokit && cd $SCRATCH/keelokit`
  2. `python3 skills/project-dashboard/scripts/dashboard.py --root . --lang en --standalone --out $SCRATCH/dash.html` (this repo's own real, adopted-but-not-approved state — current stage "Context", status "Ready for review")
  3. Run axe-core (via Playwright, `axe.run(document, {runOnly:{type:'tag',values:['wcag2aa']}})`) against `dash.html` in both `light` and `dark` `prefers-color-scheme`.
  4. Because `.sea{background:linear-gradient(...)}` (dashboard.py:1114) is a CSS gradient, axe cannot resolve a background colour for anything painted on it and reports those nodes `incomplete`, not `violation` — so also compute contrast by hand from the exact CSS custom-property values in the source, using the WCAG relative-luminance formula, sampled at each gradient stop.
- **Expected:** Normal-size text meets the WCAG 2.1 AA minimum of 4.5:1 (the a11y lens's own "contrast test" check, dimensions.md), including — and especially — the one paragraph that states the product's entire "Where we are" answer and the pill/stepper that mirror it visually.
- **Observed:** axe's `color-contrast` rule returns 17 `incomplete` nodes for exactly the hero/stepper region on every render (`#where`, `.lead`, `.lead > .pill.review`, `.next .title`, all three `.steps a > .n/.nm/.st`) — "Element's background color could not be determined due to a background gradient". Computing the real contrast from the source tokens at the gradient stop each element actually sits at:
  - `.lead` (`color:var(--foam-2)` = `rgba(246,241,232,.74)`, dashboard.py:1118) at the hero's own gradient position (`sea-0 #1A64B0`, the 0% stop, dashboard.py:1069 `--sea-0`): **3.66:1** — this is the "Current stage: Context" sentence itself.
  - `.steps .n` (`color:var(--foam-3)` = `rgba(246,241,232,.52)`, dashboard.py:1141), the "01"/"02" stage numbers in the stepper: **2.57:1** at 0% (stage 1) and **3.16:1** at 22% (stage 2) — only stage 3+ (82%+) clears 4.5:1. In a 2- or 3-stage project (the common case — greenfield has 5 stages, harness-mode has 3) most or all of the visible stage numbers fail.
  - `.sea .pill.review` (`color:#FFC08A;background:rgba(238,123,36,.2)`, dashboard.py:1203) composited onto `sea-0`: **3.56:1** — the "Ready for review" badge shown for the exact state this repo is in.
  - By contrast, `.lead em` / `.next .title` (full-opacity `--foam`) pass comfortably (5.3–17:1) at every stop — only the reduced-opacity secondary tokens fail, and only axe's blind spot (gradients) is hiding it.
- **Evidence:**
  ```
  $ node axe-run.js dash_en_repo.html   # (axe-core 4.x via Playwright/Chromium)
  "incomplete" color-contrast, 17 nodes, e.g.:
    "#where" :: "Element's background color could not be determined due to a background gradient"
    ".lead > .pill.review" :: same
    "a[href$=\"#stage-intake\"] > .n" :: same

  # manual WCAG relative-luminance calc from the literal token values at dashboard.py:1069-1074,1118,1141,1203:
  sea-0 (0%, hero top)   foam-2 .74 (.lead)      eff=#bdccd9 -> 3.66:1  FAIL (need 4.5)
  sea-0 (0%, hero top)   foam-3 .52 (.steps .n)  eff=#8cadcd -> 2.57:1  FAIL
  sea-1 (22%)            foam-3 .52 (.steps .n)  eff=#88a2c1 -> 3.16:1  FAIL
  sea pill.review (#FFC08A on rgba(238,123,36,.2) over sea-0) -> 3.56:1 FAIL
  ```
- **Where:** `skills/project-dashboard/scripts/dashboard.py:1118` (`.lead`), `:1141` (`.steps .n`), `:1203` (`.sea .pill.review`); the underlying tokens at `:1069-1074` (`--foam-2`, `--foam-3`) and the gradient itself at `:1114`.
- **Root cause (probable):** The `.foam-2`/`.foam-3` opacity tokens were tuned by eye against the flat `--abyss` colour they're mostly seen on lower down the page, not against the lighter `sea-0`/`sea-1` stops the hero itself sits on; `ui.md`'s UI-3 (a different lens) independently flagged `.sea .pill.review`'s bespoke `#FFC08A` as a token-discipline problem and assumed a themed replacement would "already contrast" — it does not, at the position the pill is actually rendered.
- **Class:** consistency
- **Should have been caught by:** dimensions.md's `a11y` row lists two checks — "axe in E2E" and "contrast test" — precisely because axe alone has this blind spot on gradients; there is no E2E or unit test for `dashboard.py`'s rendered HTML at all (confirmed against `tests/`, which covers only `guard.py`/`doctor.py`), so neither check exists in this repo today.
- **Proposed fix:** Either make `.lead`/`.steps .n`/`.steps .st` use a token whose contrast is verified against the darkest *and* lightest point of the sea gradient it can appear on (not a flat opacity of `--foam`), or add a solid scrim/shadow strong enough to guarantee 4.5:1 everywhere the gradient can place it; add a manual (or `axe --disable color-contrast` substitute that resolves gradients, e.g. Pa11y/Lighthouse's gradient-aware contrast check) test so this class of failure stops being invisible to CI.

### A11Y-4 · Every "Open file" link for a context document shares the identical accessible name, and sits nested inside another interactive control (P2)
- **Persona / context:** A screen-reader user browsing the "Context" stage's five-to-seven linked documents (`docs/context/*.md`, `.keelokit/rules.local.toml`, `.keelokit/exceptions.toml` in this repo's own fixture) using a "list of links" command (NVDA/JAWS Insert+F7, VoiceOver's link rotor) — a standard way to jump straight to a document without reading the whole page. Sha 19b332e.
- **Steps:**
  1. Same `dash_en_repo.html` fixture (7 linked context/exception documents in this repo's actual state).
  2. `page.locator('a', {hasText: 'Open file'}).allTextContents()` → 7 links, all with the exact visible text "Open file".
  3. `page.getByRole('link', { name: 'Open file' })` (Playwright's accessible-name-based role query) matches all of them identically — there is nothing in the accessible name that differs between the `docs/context/product.md` link and the `docs/context/domain.md` link.
  4. axe's `nested-interactive` rule (serious) independently flags all 7: the `<a>` sits inside a `<summary>`, which is itself a native focusable/interactive disclosure control — "Interactive controls must not be nested."
- **Expected:** Each document's "Open file" affordance has a distinct accessible name (e.g. "Open docs/context/product.md") so link-list/rotor navigation is useful, and interactive controls aren't nested inside one another (WCAG 4.1.2, axe `nested-interactive`, part of `wcag2a`).
- **Observed:** All 7 links read exactly "Open file" to a screen reader's link list, with no way to tell them apart outside of the page's normal reading order; and each sits inside the `<summary>` of `<details class="doc">`, which axe flags as invalid nesting (impact: serious, all 5-7 instances per stage). Functionally, in Chromium, clicking the link does not accidentally toggle the parent `<details>` (verified directly — `open` attribute stays `null` before/after a plain click and a Ctrl-click on the nested link), so this isn't a click-through bug in this engine, but the ambiguous/duplicate accessible name is real and independent of that.
- **Evidence:**
  ```
  $ node -e "... page.locator('a',{hasText:'Open file'}).allTextContents() ..."
  Number of links with exact text "Open file": 7 ["Open file","Open file","Open file","Open file","Open file","Open file","Open file"]
  $ node axe-run.js dash_en_repo.html
  "nested-interactive", serious, 5 nodes (per open stage), e.g.:
    ".doc:nth-child(4) > summary" :: "Element has focusable descendants"
  ```
- **Where:** `skills/project-dashboard/scripts/dashboard.py:1400-1404` (`ext_link`, hardcodes the label to `t["open_file"]`/`t["open_github"]` with no filename in it) and `:1407-1409` (`doc_block`, nests that `<a>` inside `<summary>`).
- **Root cause (probable):** `ext_link()`'s label was written for the visible case (the file path is already shown as text right next to the link, so it reads fine visually), without accounting for how an accessible name is computed and consumed independently of surrounding visible text by AT navigation modes; and the "open file" affordance was added to the same `<summary>` used for the disclosure toggle instead of a sibling control outside it.
- **Class:** consistency
- **Should have been caught by:** dimensions.md `a11y` row's "Screen reader pass on critical journeys" (reading the context documents is part of the Newcomer/Developer "review a stage" journey) — not yet run before this bug bash.
- **Proposed fix:** Give the link an accessible name that includes the file (e.g. `aria-label="{open_file_label}: {rel}"` or visually-hidden text inside the `<a>`), and move it out of `<summary>` — e.g. render the path as the `<summary>`'s only content (keeping the native disclosure semantics clean) and place "Open file" as a sibling link after the `</summary>`, inside `<details>` but not inside the interactive summary itself.

### A11Y-101 · The documented default (Artifact-mode) dashboard render drops every "Open file" link outright, for any project without a detected GitHub remote (P1)
- **Persona / context:** Every persona reading the dashboard the way it's actually meant to be
  read — dashboard.py's own docstring: "By default it is written for the Artifact tool (no
  `<html>`/`<head>`, the viewer adds them) to `.keelokit/out/dashboard.html`" — for any project
  whose `git remote get-url origin` isn't a `github.com` URL (a brand-new `/keelokit:project-new`
  project before its first `git push`, any project hosted elsewhere, or — as here — this very
