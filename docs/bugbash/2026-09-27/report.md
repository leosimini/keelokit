## Pending decisions

- **SEC-1** — How far should the guard go in catching secrets: more token formats, and secrets split across lines or edits? The README calls the guard a speed bump, and CI gitleaks scans the full history. Options: A: Add npm_, glpat-, JWT and Azure AccountKey patterns and scan each MultiEdit edit on its own. Cheap, but a split secret still gets through before commit; CI gitleaks catches it on push.; B: A, plus have the git pre-commit hook scan the full staged content of each file (git show :path) and run `gitleaks protect --staged` when gitleaks is installed. It catches split secrets before they reach history, at the cost of a slower commit.; C: Leave the list as is and rely on CI gitleaks. No work, but the documented classes stay open until push. Recommendation: B. Re-rate from P0 to P2: nothing leaks until a push, and CI gitleaks scans the full history. Still, pre-commit is the last local stop, and gitleaks already defines these patterns. **Decided 2026-09-28: B; done in 851f07e.**
- **SEC-3** — The plugin's hooks run the opened repo's own .keelokit/bin/guard.py and doctor.py on every session and tool call. Should opening a repo with Keelokit active mean trusting its .keelokit/ code? Options: A: Document it as the trust model (README 'Security model': only open repos whose .keelokit/ you trust). No code change, and it's honest.; B: The hooks run the plugin's own bundled copy against the project's rules and data. No repo code runs on open, but doctor and guard would need a --root, and an older project would run a newer script.; C: The hooks compare the project's copy with the plugin's bundled one, run the project's only when they match, and otherwise warn and run the bundled copy. Safe, but noisy on projects that haven't been upgraded yet. Recommendation: A now, since it's also true of v0.7.1 and is a plugin-directory scan note. B or C as a story. **Decided 2026-09-28: A, and B or C as story HARN-004; done in d630ede.**
